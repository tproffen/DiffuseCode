WP0 – Regression test baseline#

Part of the Python migration plan (DiffuseCode_Python_Migration_Plan.md, option B). WP0 is the safety net: before any Fortran is wrapped or refactored, we need a test suite that runs unattended, reports pass/fail reliably, and stores reference (“golden”) results to compare against.

This document has three parts:

  1. Where we are – what the existing tests/ folder covers and what happened when it was run headless on Linux.

  2. WP0 work plan – the tasks to turn it into an automated regression baseline.

  3. Progress log – what has been done so far.

mixscat is deprecated and is left out of WP0 (and of the migration).

How a test works. test_all.mac changes into each folder, runs a macro with parameters, then calls check.mac. Each macro sets LTEST_MAC = TRUE if its own check passes. A check is either:

  • a geometric value (blen, bang, atom counts), or

  • a KUPLOT comparison against a stored file: load the new result and RESULTS/<file>, then rval (R-value) below a threshold, e.g. < 0.001 for Fourier and powder, < 0.25 for the Monte-Carlo SRO examples.

Total: 30 test invocations, about 3.5 minutes on 4 cores.

1.3 Problems found#

Test-harness problems

  1. Errors are invisible to automation. A macro error ends discus_suite with exit code 0, and so does a failing check (stop in check.mac). The only pass/fail signal is text on screen (“SUCCESS in …” / “Failure, macro …”). With macro echo on, the log also contains the source of both branches of every if, so grepping for “Failure” finds false hits.

  2. One failure hides all later tests. test_all.mac is a single sequential macro, and the first error ends the run.

  3. Some sections report SUCCESS without testing anything:

    • 03.Pair_Distribution_Function – pdf.mac runs but has no check.

    • 09.Nanoparticle_refinement – system ./TEST.sh fails with Permission denied (no execute bit in git), and needs mpiexec and DISCUS_NCPU. The section still prints SUCCESS.

    • 14.Decoration/Deco_01 – all.mac has no aggregated check.

  4. Randomness is not controlled. The suite has a seed command (seed <value> or seed <a>,<b>,…, group:<n>, see lib_f90/lib_f90.hlp). Only 12 macros use it (mostly diffev_best.mac), and none of the tests in test_all.mac do. The checks therefore use loose tolerances (SRO correlation ±0.08, R < 0.25). seed does not currently make MMC runs reproducible. A quick check ran 04.SRO/SRO_0/sro.0.mac 0.7,1.5 twice with seed 1234, both at the suite prompt and directly before mmc, with OMP_NUM_THREADS=1 and 4. Every time the two runs gave different MC acceptance counts, and about half the lines of example0.stru differed. This needs debugging (task 0.5a) before golden MC data can be exact.

  5. Generated output is committed next to inputs. Example: 02.Calculation_Scattering/example3.inte sits beside RESULTS/example3.inte. tests/ is 109 MB / 2,053 files, and it is hard to tell inputs, references and leftovers apart.

  6. Coverage gaps. A rough grep finds no use of these DISCUS commands in the test macros: anis, append, asym, bragg, change, define, copy, demolecularize, interpret, inverse, kick, molecularize, patterson, perioditize, rmc, spacegroup, storage, super, switch, wyckoff. Some may be reached indirectly or under abbreviations; this needs confirming.

Build problems

  1. DIFFUSE_GRAPHICS=OFF does not work: suite/prog/CMakeLists.txt:5 always calls find_package(PGPLOT REQUIRED).

  2. make install assumes PGPLOT’s grfont.dat and pgxwin_server are in PGPLOT_DIR. On Debian/Ubuntu they are in /usr/lib/pgplot5 and /usr/bin. The binary works fine from the build tree.

  3. The build requires an FC environment variable even for re-running CMake.

Found while doing 0.2 / 0.3

  1. Start-up race (fixed). On every start discus_suite pings GitHub (check_github in lib_f90/appl_unix.f90) and wrote the answer to a fixed file, /tmp/check_github.txt. Two processes starting at the same time could delete each other’s file, and one crashed with a Fortran runtime error. The file name now includes the process ID, like the other temporary files. The ping also means every start tries to reach the network; in CI it simply fails quickly.

  2. Macros override the thread count. 04.SRO/SRO_1/sro.1.mac and SRO_3/sro.3.mac call set parallel, useomp:use, nthreads:all, which overrides OMP_NUM_THREADS. Next to other tests this over-commits the CPUs, and the OpenMP threads slow down by up to ~100× (2.4 s → 130–340 s). These tests are tagged exclusive and the runner runs them alone.

  3. Endless prompt loop. When check.mac calls stop (interactive mode) and stdin is at end of file, discus_suite prints suite > prompts forever (18 MB of log in 20 s). Batch mode never calls stop, and the runner’s timeout would catch it, but the input loop should end on EOF.

2. WP0 work plan#

Goal: one command (and one CI job) that builds DiffuseCode, runs every test in isolation, writes machine-readable results, and fails when a test fails. It also stores golden numerical outputs that later Python-API tests (WP3–WP8) can compare against.

Proposed layout#

tests/                       # existing macro tests stay where they are
  check.mac                  # [done] batch mode writes PASS/FAIL to a result file
  test_all.mac               # kept for interactive use (unchanged)
  manifest.toml              # [done] list of tests (TOML: read by Python's standard library)
  README.md                  # [done] how to run the tests
  golden/                    # 0.6: [started] reference outputs, one folder per test id
  python/                    # pytest harness
    conftest.py              #   [done] registers the manifest tags as markers
    test_legacy_macros.py    #   [done] one test per manifest entry + manifest checks
    compare.py               #   [started] R-value, golden .npz read/write (0.6)
    test_suite_python.py     #   [done] in-process Python tests against RESULTS/ and golden/
tools/
  run_legacy_tests.py        # [done] runner -> console table, JUnit XML, JSON
.github/workflows/
  tests.yml                  # [done] 0.9: build + pytest + legacy tests on claude-python-app

Suggested order#

  1. 0.2 + 0.3 – reliable pass/fail first. Everything else depends on it.

  2. 0.9 – CI right away, so regressions are seen from day one.

  3. 0.4 + 0.5a + 0.5 – remove false SUCCESS, fix seed, and make results reproducible.

  4. 0.6 – golden data, the input for the Python-API work.

  5. 0.8 + 0.10 – build and repo clean-up, then turn CI to the no-graphics build.

  6. 0.7 – coverage growth, continuing in parallel with WP1–WP3.

Reproducing the headless run#

sudo apt-get install -y gfortran cmake libfftw3-dev libhdf5-dev libreadline-dev \
    libpng-dev libx11-dev zlib1g-dev pgplot5 xvfb

mkdir -p ../DiffuseBuild && cd ../DiffuseBuild && \
FC=$(which gfortran) cmake ../DiffuseCode -DCMAKE_BUILD_TYPE=Release -DPGPLOT_DIR=/usr/lib/pgplot5 && \
make -j"$(nproc)"

Unattended, with per-test results (from the DiffuseCode folder; the runner copies each test, so tests/ stays clean):

python3 tools/run_legacy_tests.py --exe ../DiffuseBuild/suite/prog/discus_suite -j 4 --junit results.xml

Or the classic way, on a copy because the macros write output files into tests/:

cp -r tests /tmp/dc_tests && cd /tmp/dc_tests && \
PGPLOT_DIR=/usr/lib/pgplot5 xvfb-run -a "$OLDPWD/../DiffuseBuild/suite/prog/discus_suite" -macro test_all.mac < /dev/null

Flaky Monte-Carlo test in CI#

CI run 2 failed on 04.sro3 (FAIL from its own check) with exactly the code that passed in run 1; locally it passed 8 times in a row. MMC does not use the value set with seed (known bug, task 0.5a), so tests tagged mc are random and checked against statistical limits (R < 0.38, correlations within ±0.08), and they can fail by chance.

Until 0.5a is fixed, run_legacy_tests.py --retry-mc N re-runs a failed mc test up to N times. A pass on retry is counted as PASS, with the message flaky: passed on retry k; first run ... in the summary and the JUnit report. A real regression fails every attempt, and the run still fails. CI uses --retry-mc 2. Once seed works, the mc tests should get fixed seeds and the retry should be removed.

0.5a – seed (first half fixed)#

Cause 1 (fixed): seed set only part of the generator state. DISCUS uses the Fortran intrinsic random_number. gfortran’s state has 8 integers (random_seed(size=...)). ini_ran_ix (lib_f90/random_state_mod.f90) copied only the values the user gave (seed 1234 gives one) and left the other words at their clock-based values from start-up, so every run was different. The remaining words are now derived from the user’s values.

Cause 2 (open): OpenMP. With threads, MMC is still not reproducible. random_number keeps one state per thread, and random_seed(put=...) only resets the calling thread’s; the worker threads keep their own. The threads also change the shared crystal while others evaluate their moves, so the result depends on timing. A fix needs per-thread streams seeded from the seed value, plus a fixed order for applying the moves.

0.5 – seeded Monte-Carlo tests#

run_legacy_tests.py now runs every test tagged mc with seed 1234 (option --seed, or a test’s own seed in the manifest) and with OMP_THREAD_LIMIT=1. The limit also caps set parallel, nthreads:all in the SRO macros (DISCUS reports “maximum threads 1”). --no-seed gives the old behaviour. Seeded tests run on one thread, so the exclusive tests no longer need to run alone.

Checked by running all 16 enabled mc tests twice (--keep) and comparing every output file: byte-identical in both runs, apart from the generated driver macro (it contains the work-folder path) and one 04.sro3 run, see below. All pass with seed 1234.

New finding: rare broken Fourier result in 04.sro3. In one of the two runs, 04.sro3 aborted. Its MC structure (example3.stru) was identical to the other run’s, but the Fourier step (fourier.mac: random lots plus set technique:nufft) wrote 1530 Infinity values and blocks of zeros to example3.inte, and NaN to example3.3DPDF; kex3.mac then failed on zmax[3]. 14 more seeded runs (6 serial, 8 with 4 at a time) all gave the same correct result, so it is rare (1 in about 17 so far). It may also explain the original CI failure of 04.sro3 (run 2). Needs its own investigation: uninitialised memory or a race in the lots/NUFFT path are candidates. Until then, CI keeps --retry-mc 2.

  • NUFFT agrees with the standard technique for the 50×50 layer on the 04.sro3 grid; known failure (strict xfail) for small crystals.

Findings (details in WP0_Test_Coverage_Gaps.md):

  1. NUFFT gives wrong maps for small crystals on many grids (e.g. Ni 4×4×4, hk0 −3…3: R = 1.7), but is exact for others (10×10 cells, the 50×50 layer, a 9×9 grid over 0…4). The default technique is unaffected. Probably related to the rare Infinity/NaN map in 04.sro3, which uses NUFFT. Needs fixing before WP4 wraps the technique option.

  2. SHELX export writes every atom of the cell together with the space-group symmetry (and occupancy 0.5): re-reading CuO gives 32 atoms instead of 8.

  3. disp on does not switch on anomalous dispersion; only disp anom does. Any macro using disp on silently gets no dispersion.

  4. Fractions in the legacy atom format are silently misread. .cell files have two atom formats. The comma format with a column header (atoms x, y, z, Biso / co 1./3., 2./3., 0.0, 1.0) runs the values through the interpreter, so 1./3. works. The legacy format (bare atoms, values separated by blanks) uses a list-directed read, which stops at /: 1./3. becomes 1., without a warning. Mixing the two (bare atoms with commas, or a header with blanks) gives an error. 01.Simulation/calculate.cell uses the legacy format and gets Co at (0,0,0) instead of (1/3,2/3,0).

  5. export.mac: its failures are mostly outdated reference files and typos; two checks pass falsely because compare_files.mac treats a missing file as “no differences”.

  6. Crystal.atoms() (Python) failed on structures with molecules; fixed.

Checked: pytest tests/python 80 passed, 2 known failures, the same with OMP_NUM_THREADS 1 and 4.

0.8 – build fixes#

  • DIFFUSE_GRAPHICS=OFF builds without PGPLOT and X11 (finding 7). suite/prog/CMakeLists.txt looked for PGPLOT unconditionally and linked PGPLOT, X11 and PNG; python/CMakeLists.txt linked them into the Python module too. Both now do so only with graphics; KUPLOT already had *_nographic.f90 replacements. ldd of discus_suite and suite_python*.so shows no PGPLOT, X11 or PNG.

  • FC is no longer required (finding 9). CMake picks the Fortran compiler itself (-DCMAKE_Fortran_COMPILER, else FC, else the first one found). The old set(CMAKE_Fortran_COMPILER $ENV{FC}) after enable_language had no effect anyway.

  • PGPLOT install paths (finding 8). make install looks for grfont.dat and pgxwin_server in PGPLOT_DIR and the usual system places (Debian/Ubuntu: /usr/lib/pgplot5, /usr/bin), skips a missing file with a warning, and installs nothing PGPLOT-related without graphics. -DPGPLOT_DIR is no longer needed on Ubuntu.

  • CI has a second job, python-nographics: no PGPLOT, X11 or Xvfb packages, DIFFUSE_GRAPHICS=OFF, an ldd check, pytest and the docs. The linux job keeps the graphics build for the legacy macro tests, now without FC, CC, CXX or PGPLOT_DIR.

04.sro3 broken Fourier result, now reproducible. On this machine, tools/run_legacy_tests.py --id 04.sro3 (seed 1234, one thread) aborts on every run, on both the graphics and the no-graphics build: example3.inte gets ~1500 Infinity values and example3.3DPDF is all NaN. It is unrelated to graphics. This is the case to debug, with a debug build (-DDEBUG=ON, -fcheck=all).
